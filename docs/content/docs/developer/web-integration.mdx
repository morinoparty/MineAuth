This guide explains how to integrate MineAuth OAuth authentication with web applications. We'll demonstrate using [better-auth](https://www.better-auth.com/) as an example.

## Overview

MineAuth provides standard OpenID Connect (OIDC) endpoints. You can integrate with any OAuth2/OIDC compatible library.

```mermaid
sequenceDiagram
    participant User
    participant Website
    participant MineAuth
    User->>Website: Click Login
    Website->>MineAuth: Authorization Request
    MineAuth->>User: Show Login Form
    User->>MineAuth: Enter Credentials
    MineAuth->>Website: Authorization Code
    Website->>MineAuth: Token Request
    MineAuth->>Website: Access Token + ID Token
    Website->>User: Login Complete
```

## Prerequisites

- OAuth client created in MineAuth ([Quick Start Guide](/docs/administrator/quick-start))
- MineAuth server accessible from your web application
- Node.js project with better-auth installed

## Setup with better-auth

### Install Dependencies

```bash
npm install better-auth @better-auth/generic-oauth
```

### Configuration

Create your auth configuration file:

```typescript title="lib/auth.ts"
import { betterAuth } from "better-auth";
import { genericOAuth } from "@better-auth/generic-oauth";

export const auth = betterAuth({
  // Your application's base URL
  baseURL: process.env.REDIRECT_AUTH_URL,
  // Secret for signing sessions
  secret: process.env.AUTH_SECRET,
  plugins: [
    genericOAuth({
      config: [
        {
          // Provider identifier
          providerId: "mineauth",
          // OAuth client ID from MineAuth
          clientId: process.env.MINEAUTH_CLIENT_ID!,
          // Leave empty for Public clients (PKCE)
          clientSecret: "",
          // Enable PKCE for Public clients
          pkce: true,
          // MineAuth OpenID Connect discovery URL
          discoveryUrl: `${process.env.MINEAUTH_URL}/.well-known/openid-configuration`,
        },
      ],
    }),
    // Add other plugins as needed
  ],
});
```

### Environment Variables

Set the following environment variables:

```bash title=".env"
# Your website URL
REDIRECT_AUTH_URL=http://localhost:3000

# Random secret for session signing
AUTH_SECRET=your-random-secret-here

# MineAuth client ID (from /ma client create)
MINEAUTH_CLIENT_ID=your-client-id

# MineAuth server URL
MINEAUTH_URL=https://your-minecraft-server.com:8443
```

## Client Type Configuration

### Public Client (Recommended for Web)

For browser-based applications, use PKCE without a client secret:

```typescript
genericOAuth({
  config: [
    {
      providerId: "mineauth",
      clientId: process.env.MINEAUTH_CLIENT_ID!,
      clientSecret: "", // Empty for Public clients
      pkce: true,       // Required for Public clients
      discoveryUrl: `${process.env.MINEAUTH_URL}/.well-known/openid-configuration`,
    },
  ],
}),
```

### Confidential Client

For server-side applications with secure secret storage:

```typescript
genericOAuth({
  config: [
    {
      providerId: "mineauth",
      clientId: process.env.MINEAUTH_CLIENT_ID!,
      clientSecret: process.env.MINEAUTH_CLIENT_SECRET!,
      pkce: false,
      discoveryUrl: `${process.env.MINEAUTH_URL}/.well-known/openid-configuration`,
    },
  ],
}),
```

A Confidential client can log users in without any extra setup. To also call the [token introspection endpoint](/docs/developer/oauth/introspect), a server administrator must grant it the permission with `/ma client introspection allow <clientId>`, which requires `mineauth.client.introspection`. Without it, the endpoint responds with `403 unauthorized_client`.

## Login Button Example

```tsx title="components/LoginButton.tsx"
import { authClient } from "@/lib/auth-client";

export function LoginButton() {
  const handleLogin = () => {
    authClient.signIn.oauth2({
      providerId: "mineauth",
    });
  };

  return (
    <button onClick={handleLogin}>
      Login with Minecraft
    </button>
  );
}
```

## Redirect URI Patterns

A client can have several registered redirect URIs, and a request is accepted when its `redirect_uri` matches any of them.
For example, you can register both the production URL and `http://localhost:3000/...` for local development.

Each registered redirect URI is validated in two steps: an exact string match first, then as a regular expression. When used as a regular expression, `(/.*)?` is appended to the registered value (or `.*` if it already ends with `/`), so a request can use the value itself or any of its sub-paths.

A `redirect_uri` containing `#` is always rejected, whatever is registered.

A registered value whose scheme contains `.` or `+`, such as the custom scheme `com.example.app://callback`, is never evaluated as a regular expression. Those characters would otherwise let the scheme match another one: `h.tp://evil.example/cb` would match `http://evil.example/cb`. Such a value is compared as plain text instead. A request matches when it equals the registered value or is a sub-path of it, such as `com.example.app://callback/done`. A leading `^` is ignored.

Regular expressions are useful for platforms with per-deployment preview URLs, such as Cloudflare Workers:

```
https://(?:[0-9a-f]{8}-)?myapp\.example\.workers\.dev/api/auth/oauth2/callback/
```

- `(?:[0-9a-f]{8}-)?` matches the optional 8-character hex prefix of preview deployments, while still allowing the stable domain.
- Ending the pattern with `/` means only `.*` is appended, so `.../callback/MineAuth` matches as a sub-path, while `.../callback` without the slash does not match.

Because `http` and `https` values are also evaluated as regular expressions, an unescaped `.` matches any character. Write dots as `\.` when the host must match exactly.

### Pattern Registration Rules

A value that cannot be read as a URI with a host is treated as a regular expression pattern. The following rules are checked at registration, in addition to the [redirect URI rules](/docs/administrator/quick-start#redirect-uri-rules):

- A pattern must start with `https://`, or with `http://` followed by a loopback host. A leading `^` is allowed. Prefixes such as `https?://` and `httpx` are rejected.
- In an `http://` pattern, the loopback host must be written literally as `localhost`, `127\.0\.0\.1`, or `\[::1\]`. An optional port written as digits, `:\d+`, `:[0-9]+`, or an optional group such as `(:\d+)?` may follow. After that, the pattern must end or continue with a `/` that is not optional. For example, `http://localhost:\d+/callback` is accepted, while `http://localhost:.*/callback` is rejected because it also matches `http://localhost:x@evil.example/callback`.
- A `|` at the top level of a pattern is rejected, because the alternatives after it would not be restricted by the start of the pattern. Write alternatives inside a group, such as `https://(a|b)\.example\.com/callback`.
- A pattern cannot contain `#`.

## Troubleshooting

### Common Issues

**"Invalid redirect URI"**
- Ensure the redirect URI in your application matches exactly what was registered in MineAuth
- Check for trailing slashes
- If you registered a regular expression pattern, remember that `(/.*)?` is appended, or `.*` if the pattern ends with `/` (see [Redirect URI Patterns](#redirect-uri-patterns))
- Remove any `#` fragment from the `redirect_uri`

**"PKCE verification failed"**
- Make sure `pkce: true` is set for Public clients
- Verify the client type matches your MineAuth client configuration

**"Discovery URL not reachable"**
- Verify MineAuth server is running and accessible
- Check firewall settings for the MineAuth port
